# Obsi Sync: плагин Obsidian для obsi-mcp

Плагин делает три вещи:

1. **E2EE-синхронизация** нескольких независимых vault'ов с сервером obsi-mcp. Шифрование на устройстве
   (`rclone-base64` по умолчанию, `openssl-base64` как вариант), сервер видит только шифротекст.
   Движок синхронизации — форк Apache-2.0 версии Remotely Save (см. `NOTICE`).
2. **AI Available**: по вашим правилам публикует на сервер открытым текстом только разрешённые заметки
   и вложения, чтобы их мог читать и искать MCP-клиент.
3. **Применение правок от MCP**: забирает `write_note` из очереди сервера и применяет их в vault.

Работает на десктопе и на мобильных (`isDesktopOnly: false`, HTTP через `requestUrl`, без модулей Node).

## Установка

Сборка:

```bash
cd plugin
npm install
npm run build        # tsc --noEmit + esbuild, на выходе main.js
```

Скопируйте три файла в vault:

```
<vault>/.obsidian/plugins/obsi-sync/main.js
<vault>/.obsidian/plugins/obsi-sync/manifest.json
<vault>/.obsidian/plugins/obsi-sync/styles.css
```

Перезапустите Obsidian, включите плагин «Obsi Sync» в «Community plugins».

## Настройка

Пока плагин не настроен, он ничего не делает и не показывает ошибок: в статус-баре «Obsi: set up»,
кнопка синхронизации и клик по статусу открывают окно настройки.

**Первый запуск.** Появляется окно приветствия с двумя кнопками:
* «Not now» — окно закрывается и больше само не появляется. Вернуться: команда «Obsi Sync: Set up»
  или кнопка «Set up» в настройках.
* «Connect a server» — URL сервера и токен устройства → «Check connection» → выбрать vault сервера →
  пароль шифрования → «Save and sync». Весь Obsidian-vault становится корневым mount'ом этого vault'а.
  AI Available остаётся выключенным, пока его не включить в настройках.

Остальное (несколько mount'ов, AI, admin) — по желанию, в «Settings -> Obsi Sync».

1. **Connection.** Укажите URL сервера (например `https://notes.example.com`) и токен устройства
   (`kind=device`, гранты `read` и `write` на нужные vault'ы). Кнопка «Test» вызывает `/api/v1/me`
   и показывает, какие гранты есть у токена.
2. **Vault mounts.** Нажмите «Refresh», затем «Add mount»:
   * **Folder**: папка в этом Obsidian-vault. Пусто означает весь vault (корневой mount).
   * **Server vault**: выпадающий список из `GET /vaults`.
   * **Password**: ключ шифрования этого vault'а. Хранится только на устройстве. Потеряете пароль,
     потеряете данные: сервер расшифровать их не может.
   * **Encryption method**: `rclone` (рекомендуется) или `openssl`.
3. Включите «Sync enabled». Синхронизация идёт при старте (с задержкой), по интервалу, по кнопке на
   ленте (иконка обновления) и по команде «Obsi Sync: Sync now».

Строка статуса внизу показывает ход синхронизации. Если сервер недоступен, mount помечается ошибкой
и просто повторяется при следующем запуске, остальные mount'ы это не блокирует.

Конфликты: «Keep newer» (по умолчанию) или «Keep larger». Режима «хранить обе версии» нет.

Безопасность: параметр «Safety limit» прерывает синхронизацию, если она изменила бы или удалила слишком
большую долю файлов (работает от 10 файлов).

### Несколько vault'ов (mount'ы)

Каждый mount синхронизирует свою папку со своим серверным vault'ом, со своим паролем и со своей
историей синхронизации (ключ в локальной БД: `vaultId`). Mount'ы идут по очереди, самые вложенные первыми.

* Вложенный mount исключается из родителя. Если папка `Work` смонтирована отдельно, корневой mount её
  не трогает: ни не загружает, ни не удаляет (даже если раньше она лежала в корневом vault'е).
* Корневой mount дополнительно синхронизирует `.obsi/` (там `ai-rules.json`). Папка `.obsidian`
  синхронизируется только при включённой опции «Sync Obsidian config folder».
* Перенос файла между vault'ами это удаление в одном и создание в другом. Второй vault шифрует файл
  своим ключом.
* Ссылки между vault'ами обычные Obsidian-ссылки по пути, в отдельно открытом sub-vault они могут быть битыми.

### Экспорт и импорт mount'ов

«Copy export» копирует JSON `{format, serverUrl, mounts: [{path, vaultId, vaultName, encryptionMethod}]}`.
Паролей и токенов в нём нет. На втором устройстве вставьте строку в поле и нажмите «Import», затем введите
пароли и токен устройства.

### Недоверенное устройство

1. На сервере (раздел Admin или CLI) выдайте токену `kind=device` грант только на нужный sub-vault.
2. На устройстве создайте отдельный пустой Obsidian-vault, поставьте плагин, укажите URL и этот токен.
3. Добавьте один mount: Folder пусто (корень), Server vault: sub-vault, пароль только от него.

Устройство не знает ключей и токенов остальных vault'ов, и в его корне нет `.obsi/ai-rules.json`,
поэтому оно **ничего не публикует** в AI Available.

## Раздел Admin (необязательный)

Раскройте «Admin» и вставьте admin-токен. Отсюда можно: создать vault, включить или выключить RAG для
vault'а, задать embedding-настройки сервера (base URL, ключ, модель), создать токены `device` и `mcp`
с грантами на каждый vault (device: `read`/`write`; mcp: `list`/`search`/`read`/`write`) и отозвать токены.
Новый токен показывается один раз. Admin-токен хранится в `data.json` плагина этого устройства, на
мобильном или чужом устройстве его лучше не вводить.

## AI Available

Включается переключателем «AI Available enabled» (по умолчанию выключено). Выключили, значит публикация
остановлена; кнопка «Clear published data» вызывает `POST /vaults/{id}/ai/clear` для всех смонтированных
vault'ов.

Публикуют только устройства, у которых в **корневом mount'е** есть `.obsi/ai-rules.json` и он корректен.
Если в файле есть ошибки (битое правило), публикация не выполняется (fail closed).

Публикация для каждого vault'а: считается набор `{относительный путь -> sha256}`, сравнивается с
`GET /ai/manifest`, различия заливаются `PUT`, лишнее удаляется `DELETE`. Ответ `409 stale_publish`
пропускается. Запуск: при изменении, создании, переименовании и удалении файла и при изменении
frontmatter (с задержкой), при изменении правил, после синхронизации и при старте. Файлы больше
«Max file size to publish» (25 МБ по умолчанию) не публикуются.

### Формат `.obsi/ai-rules.json`

```json
{
  "version": 1,
  "mode": "deny_by_default",
  "rules": [
    { "id": "r1", "type": "folder",   "effect": "include", "path": "Projects" },
    { "id": "r2", "type": "folder",   "effect": "exclude", "path": "Projects/Secret" },
    { "id": "r3", "type": "property", "effect": "exclude", "key": "private", "op": "equals", "value": true },
    { "id": "r4", "type": "property", "effect": "include", "key": "tags", "op": "contains", "value": "ai" }
  ]
}
```

* `mode`: `allow_by_default` или `deny_by_default`. Применяется только когда ни одно правило не подошло.
* `folder`: `path` в едином дереве vault'а (может указывать внутрь mount'а), совпадает с самой папкой и
  всем внутри. Пустой путь означает весь vault.
* `property`: по frontmatter заметки. `op`: `exists`, `equals`, `contains` (для списков и строк).
  Ключи без учёта регистра, `equals` и `contains` для строк тоже без учёта регистра. Для `tags`
  работают и `#tag`, и `tag`, вложенные теги (`ai/deep` подходит под `ai`) и теги из тела заметки.
* Для **заметки** (`.md`): собираются все подошедшие правила. Есть `exclude`, значит запрещено
  (приватность важнее, неважно, folder это или property). Иначе есть `include`, значит разрешено.
  Иначе решает `mode`.
* Для **вложения** (не `.md`): разрешено, если на него ссылается хотя бы одна разрешённая заметка
  (`metadataCache.resolvedLinks`) и его не задевает ни одно `exclude`-правило, применимое к вложениям.
  Правила `property` к вложениям не применяются.
* Неизвестный тип правила с `exclude` считается сработавшим (безопасная сторона), с `include` игнорируется.
* `addToNewNotes: true` у правила-чекбокса (`property`, `op: "equals"`, `value: true|false`): в каждую
  новую пустую заметку добавляется этот property в «невыбранном» состоянии (обратное `value`), показанный
  как чекбокс. Отметил чекбокс — правило сработало. Заметки, созданные сразу с текстом (шаблоны, daily
  notes, правки от MCP, синхронизация), не трогаются — в шаблон property добавьте сами.

### Стартовые правила

Кнопка «Create» (если файла правил ещё нет) создаёт:

```json
{ "version": 1, "mode": "deny_by_default",
  "rules": [ { "id": "r1", "type": "property", "effect": "include", "key": "ai", "op": "equals", "value": true, "addToNewNotes": true } ] }
```

То есть AI ничего не видит, кроме заметок с отмеченным чекбоксом `ai`; в новых заметках этот чекбокс
появляется сам. В редакторе правил у правил-чекбоксов есть переключатель «Add to new notes».

Правила редактируются в настройках (режим, список правил, «Save rules») или прямо в файле. Новые типы
правил добавляются регистрацией `RuleMatcher` в `src/ai/rules.ts` (`RuleMatcherRegistry`).

## Правки от MCP

Если у токена устройства есть грант `write` на vault, плагин после синхронизации и по таймеру
(«Poll pending MCP changes», по умолчанию 2 минуты) читает `GET /changes?status=pending` и для каждой
правки:

* проверяет путь (без `..`, без скрытых папок, только `.md`) и что он принадлежит этому vault'у;
* проверяет, что путь разрешён правилами (и сейчас, и после правки, с новым frontmatter), иначе `rejected`;
* `update`: sha256 локального файла должен совпасть с `base_version`, `create`: файла быть не должно,
  иначе `conflict`;
* применяет через `vault.modify` / `vault.create` (создаёт родительские папки) и отправляет `ack` с `new_version`.

Изменение дальше уходит на другие устройства обычной E2EE-синхронизацией и перепубликуется.

## Разработка

```bash
npm test             # mocha + tsx: правила, mount'ы, публикация, правки, синхронизация через шифрование
npm run build        # tsc --noEmit + esbuild -> main.js
npm run dev          # esbuild --watch
```

Чистая логика (правила, диффы, mount'ы, решения по правкам) не зависит от Obsidian и покрыта тестами.
Код Obsidian-слоя (`main.ts`, `syncManager.ts`, `ui/`, `ai/publisher.ts`, `ai/applier.ts`) руками в живом
Obsidian не прогонялся.
